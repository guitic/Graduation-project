# 基于 Web 的学业导师智能点评分析系统 —— 设计文档

> 版本：v1.0（对应代码基线：后端 `demo` profile 可零依赖启动，前端可 `npm run build`）
> 适用：2027 届本科毕业设计（软件工程）

---

## 一、摘要

本系统面向高校学业指导与教务管理场景，解决三个问题：

1. **流程规范**：导师点评的提交、审核、发布、查看缺乏统一状态与留痕，容易出现「审核过了但没发给学生」「发出去又发现写错了收不回」。
2. **文本价值**：点评文本长期沉睡，无法回答「整体指导氛围如何」「哪些主题被反复提及」。
3. **隐私边界**：小样本聚合会反向暴露个人信息，必须在展示层设置门槛。

系统以 **双维度状态机** 规范流程，以 **词典法情感分析 + 实时词频** 挖掘文本，以 **k=5 隐私门槛** 约束展示，并以 **可解释性**（命中词、权重、否定）保证分析结果可被人工复核。

## 二、角色与权限

| 角色 | 可做 | 数据范围 |
| --- | --- | --- |
| 学业导师 TEACHER | 写点评、存草稿、提交、退回后修改重提、查看本人点评与审核意见 | 仅 `teacher_student` 中本人指导的学生 |
| 教务管理员 ADMIN | 审核（通过/仅通过/退回/驳回）、发布/撤回、统计报表、师生关系维护 | 全量 |
| 学生 STUDENT | 查看本人已发布点评 | 仅本人 + 已发布 |

> 权限判定在 **Service 层**（`AuthContext` + `CommentScope`），不依赖前端隐藏菜单，也不依赖路由分组。

## 三、总体架构

```text
浏览器
  └─ Vue 3 + Vite + Element Plus + ECharts（echarts-wordcloud）
       └─ REST /api  （统一 {code,msg,data}，令牌头 satoken）
            └─ Spring Boot 3.2.5
                 ├─ Controller（Auth/Comment/Audit/Report/Person/Student）
                 ├─ Service（业务 + 状态机 + 统计口径）
                 │    └─ analysis/（SentimentLexicon / SentimentAnalyzer / WordSegmenter / PrivacyFilter）
                 ├─ MyBatis-Plus Mapper
                 └─ MySQL 8（默认） / H2 内存库（demo）
```

- **鉴权**：Sa-Token，登录后返回 `token`，前端存 `localStorage` 并放入 `satoken` 请求头。
- **响应**：所有响应（含错误）均为 HTTP 200 + `{code,msg,data}`；`code=0` 成功，401 未登录，403 越权。
- **零依赖演示**：`application-demo.yml` 使用 H2 内存库 + 自动建表 + 种子数据，答辩现场无需装 MySQL。
- **建表与演示能力隔离**：`db/schema.sql` 是「先 drop 再 create」的重置脚本，因此只有 demo 由 `spring.sql.init` 自动执行；默认（MySQL）profile 为 `mode: never`，首次部署手动执行脚本——否则每次重启都会静默清空业务数据。种子数据与登录页演示账号统一受 `app.demo-seed.enabled` 控制，默认关闭。

## 四、数据库设计

表名与源文档的差异：`user` → `sys_user`，`class` → `clazz`（规避 SQL 保留字）。

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `sys_user` | 账号与角色 | username, password(BCrypt), role, status |
| `major` / `clazz` | 专业 / 班级 | major.college, clazz.major_id, grade |
| `teacher` / `student` | 人员档案 | teacher_no/student_no, clazz_id, status |
| `teacher_student` | **指导关系（数据权限依据）** | teacher_id, student_id, status |
| `comment` | 点评主体 | status, submit_at, **published_at**, **withdrawn_at**, version |
| `comment_audit` | 事件流（非仅审核） | **action_type**(7 值), result, opinion, before_content, audit_at |
| `comment_sentiment` | 分析结果 | **content_hash**, method_version, label, score, confidence, low_confidence |
| `sys_oper_log` | 操作留痕 | action, target_type, target_id, user_id |

**关键取舍：不建词频缓存表。**
派生数据没有单一失效源：点评退回改稿、撤回、再发布都会让缓存与业务状态不一致，且这类错误**不报错**、图看起来完全正常。在百条量级下实时分词是毫秒级，缓存没有收益。

## 五、状态机：为什么「通过」不等于「发布」

### 5.1 两个正交维度

- `status`：内容是否通过审核（DRAFT / PENDING / APPROVED / RETURNED / REJECTED）
- `published_at`：是否已推送给学生（NULL = 未发布，非 NULL = 已发布）

> 若把「已通过」与「已发布」合并成一个状态，**「撤回」将无法实现**——撤回后既不是「待审核」也不是「已通过」，没有合法落点。拆成两个维度后，撤回只需把 `published_at` 置回 NULL 并记录 `withdrawn_at`，内容仍保持 APPROVED。

### 5.2 状态与动作

```text
DRAFT ──submit──▶ PENDING ──approve(publish=true)──▶ APPROVED + published_at
  ▲                  │
  │                  ├──approve(publish=false)──▶ APPROVED（待发布）
  │                  ├──return──────────────────▶ RETURNED ──修改重提──▶ PENDING
  │                  └──reject──────────────────▶ REJECTED（终态）
  └──────────────────────────────────────────────────────────────

APPROVED + published_at ──unpublish──▶ APPROVED + withdrawn_at（学生立即不可见）
APPROVED + withdrawn_at ──publish(≥5)──▶ APPROVED + published_at（再发布）
```

### 5.3 七个事件类型（`comment_audit.action_type`）

`SUBMIT` / `APPROVE_ONLY` / `APPROVE_PUBLISH` / `RETURN` / `REJECT` / `PUBLISH` / `WITHDRAW`

> 事件流而非「审核表」：提交、发布、撤回都不是「审核」，但都必须可追溯。用一张事件表统一承载，前端时间线按角色裁剪（学生端不下发审核意见与快照）。

## 六、情感分析设计

### 6.1 方法：情感词典法（可解释、可复现）

1. **分词**：HanLP portable（离线），过滤停用词、标点、虚词。
2. **隐私过滤**：先 `PrivacyFilter.normalize`（全角→半角、空白折叠），再对姓名/学号/手机号/身份证/邮箱脱敏。
3. **词典匹配**：正向词 +、负向词 −；否定词（不/没/无…）与程度词（很/非常/比较…）**向前回看 2 个词**作用于情感词。
4. **累计净得分** `score`，按阈值映射：
   - `score ≥ +1.5` → 正向 POSITIVE
   - `score ≤ −1.5` → 负向 NEGATIVE
   - 其余 → 中性 NEUTRAL
5. **置信度**：落在阈值灰区的标注 `low_confidence=1`，供人工复核。

### 6.2 复用与失效：双匹配

`comment_sentiment` 记录 `content_hash`（正文 SHA-256，归一化后计算）与 `method_version`。
**只有两者同时匹配才复用**：正文改了（hash 变）或方法升级了（version 变）都必须重算。单一条件匹配会在「改了一个字」或「升级词典」时静默沿用旧结果。

### 6.3 可解释性展示

审核详情抽屉展示：净得分、置信度、正/负命中数、**命中词列表（含权重与是否被否定）**，并标注方法版本。这让「为什么判为正向」可被逐条复核，而不是黑箱结论。

### 6.4 评价指标与实测结果（论文口径）

在人工标注验证集（75 条，三类均衡）上计算 **准确率 / 精确率 / 召回率 / F1**，并报告 **混淆矩阵** 与 **Cohen's Kappa**。

**实测**：准确率 **82.7%**、Kappa **0.74**（高度一致）；正向 F1 0.96、中性 0.79、负向 0.72；正向/负向 Precision 均 1.00。13 条错分全部为「弱极性判中性」，**无极性反转**。阈值敏感性显示负向阈值放宽到 -1.0 可达 90.7%，但同集调参有过拟合风险，故保留 -1.5 保守默认。详见 `deliverables/情感分析评估报告.md`。

> 82.7% 高于最初设定的 65%~75%，原因是验证集为作者构建、句子较清晰；真实模糊数据的准确率预计回落至该区间。

## 七、统计口径与隐私门槛

### 7.1 单一口径

所有报表只经 `CommentScope.published()`：

```sql
status = 'APPROVED' AND published_at IS NOT NULL
```

饼图、趋势、词云、下钻共用同一入口，避免「饼图算 56、趋势算 58」这类数字对不上。

### 7.2 单一门槛 `analysis.min-sample = 5`

- 一个配置键，同时作用于：情感分布饼图、趋势图级、趋势桶级、词云、词条下钻。
- 样本不足时：**占比字段返回 null**（前端拿不到数），而不是「后端算了、前端不显示」。
- 趋势图：**数量柱永远可画**（数量本身不敏感），但**比率线**在整图样本 <5 时整条不画；稀疏桶为 null（断线）。

### 7.3 两层门禁必须分开

| 层 | 判定依据 | 表现 |
| --- | --- | --- |
| 图级 | 整体样本量 | 整张图空态 |
| 桶级（下钻） | **该时间桶/该词下的样本量** | 该点下钻禁用 |

> 主班整体 40 条足以放行，但某个月可能只有 2 条；点进去就是 2 个学生的完整点评，等同于直接暴露个人。**整体充足 ≠ 单个桶充足。**

### 7.4 演示种子与门槛的对应

| 班级 | 已发布 | 分布 | 用途 |
| --- | --- | --- | --- |
| 计科2201 | 40 | 8/11/7/9/5 | 健康形态（每月 ≥5） |
| 计科2205 | 5 | 单月 | 阈值点（恰好放行） |
| 计科2207 | 4 | 单月 | 下边界（三图全空） |
| 计科2208 | 7 | 6+1 | 桶级探针（前月可钻、后月禁用） |

## 八、关键决策表（过程收敛结果）

| # | 议题 | 决策 | 理由 |
| --- | --- | --- | --- |
| 1 | 通过 vs 发布 | 拆为 `status` + `published_at` | 否则撤回无落点 |
| 2 | 撤回 | 列为 P0，可逆 | 误发布必须能收回 |
| 3 | 审核意见字数 | 通过≥5 / 仅通过≥10 / 退回≥10 / 驳回≥20 | 越接近「不可逆」，理由要求越高 |
| 4 | 撤回 / 再发布理由 | 撤回≥10 / 再发布≥5 | 「为何压下」与「为何放回」都要可查 |
| 5 | 审核意见预填 | **不预填**，仅 placeholder | 预填会把「复制粘贴」当「已审核」 |
| 6 | 门槛配置 | 单一 `min-sample=5` | 三套阈值必然出现「饼图给了、词云不给」 |
| 7 | 词频缓存 | 不建表，实时聚合 | 派生数据无失效源 |
| 8 | 分析复用 | `content_hash` + `method_version` 双匹配 | 单条件会静默沿用旧结果 |
| 9 | 学生端字段 | 仅正文/导师/时间/学期/主题 | 审核意见与情感标签会引发语义错位 |
| 10 | 趋势含当月 | 含当前未完结月，虚线/斜纹标注 | 「当月持续更新」必须可见 |
| 11 | 批量发布 | **不提供** | 批量 `WHERE id IN(...)` 会绕过逐条状态校验 |
| 12 | 演示主班 | 每月均 ≥5，不挖稀疏洞 | 主班只回答「健康时什么样」 |
| 13 | 桶级门禁 | 按桶判定，不按整体 | 整体充足 ≠ 单桶充足 |
| 14 | 词云样本 | 与情感共用 5 | 2~4 条的高频词≈原文关键词，放宽收益为零 |

## 九、接口设计（摘要）

统一响应 `{code,msg,data}`，`code=0` 成功。分页返回 `{records,total,page,size}`。

| 模块 | 代表接口 |
| --- | --- |
| 认证 | `POST /api/auth/login`、`GET /api/auth/me`、`GET /api/demo/accounts` |
| 元数据 | `GET /api/meta/limits`（审核意见字数门槛 + 隐私样本量，前端文案的唯一来源） |
| 点评 | `GET /api/comment/page|admin-page|student-page`、`POST/PUT/DELETE /api/comment`、`POST /api/comment/{id}/submit` |
| 审核 | `GET /api/audit/pending|unpublished|published`、`POST /api/audit/{id}/approve|return|reject|publish|unpublish`、`GET /api/audit/{id}/history` |
| 报表 | `GET /api/report/dashboard|sentiment|trend|audit-stat|wordcloud|word-detail|trend-point`、`GET /api/report/comment/{id}/sentiment` |
| 人员 | `GET /api/person/teachers|my-students|students|clazz|terms`、`POST /api/person/bind`、`DELETE /api/person/bind/{id}` |
| 学生 | `GET /api/student-comment/page`、`GET /api/student-comment/{id}` |

**并发控制**：审核/提交采用「条件更新 + 影响行数判定」（`WHERE status = ?`），影响 0 行即抛 409「状态已变化」，避免两人同时审核造成状态覆盖。

## 十一、测试基线（验收要点）

1. **状态机**：草稿→提交→待审→通过（仅通过）→待发布→发布→撤回→再发布，每步状态与可见性正确。
2. **双维度**：仅通过后学生端不可见、统计不含；发布后可见且纳入；撤回后立即不可见且统计减少。
3. **门槛**：2207（n=4）三图空态；2205（n=5）放行；把 `min-sample` 改为 6，四张图必须同时变化。
4. **桶级**：2208 前月 6 条可下钻、后月 1 条禁用；2201 任一月（均 ≥5）可下钻。
5. **越权**：导师访问非指导关系学生 → 403；学生访问他人点评 → 403/404；教务接口非管理员 → 403。
6. **学生端字段**：详情与列表均无审核意见、无情感标签。
7. **并发**：两条审核请求同时提交同一 PENDING 点评，后到者收到 409。
8. **可解释**：任一条已发布点评的分析依据可展开，命中词与权重非空（中性除外）。

> **自动化覆盖**：第 1、2、7 条已由 `AuditStateMachineTest`（21 条）与 `AuditPermissionTest`（10 条）固化为 `mvn test` 断言，
> 第 3、4 条由种子数据（2205/2207/2208）钉住阈值两侧，并可用 `--analysis.min-sample=60` 现场演示"一个配置改四张图"。

## 十二、局限与扩展

- **词典法局限**：反讽、双重否定、领域新词识别弱；通过「低置信 + 人工复核」兜底。扩展项：轻量分类模型对比实验、Spring AI 辅助摘要（仅作建议，不替代基础路径）。
- **词频无权重**：当前为原始词频，未做 TF-IDF；可在数据量增大后引入。
- **导出**：报表导出为扩展项，导出明细须遵循角色权限。
- **单机部署**：毕设范围内部署为单实例；生产化需引入缓存、异步分析与更细的审计。
