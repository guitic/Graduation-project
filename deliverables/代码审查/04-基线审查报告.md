### P0-2 · `/api/audit/{id}/history` 缺失权限校验（越权读取审核意见）

| 项 | 内容 |
| --- | --- |
| 位置 | `AuditController.java:91-94` → `AuditService.java:269-289` |
| 级别 | **P0（安全漏洞）** |

**现象**

```java
// AuditController.java:91
@GetMapping("/{id}/history")
public R<List<CommentDtos.AuditItem>> history(@PathVariable Long id) {
    return R.ok(auditService.audits(id));      // ← 无 requireAdmin()
}

// AuditService.java:269
public List<CommentDtos.AuditItem> audits(Long commentId) {
    List<CommentAudit> list = auditMapper.selectList(...);
    for (CommentAudit a : list) {
        it.setOpinion(a.getOpinion());          // ← 审核意见原样返回
        it.setBeforeContent(a.getBeforeContent()); // ← 修改前正文原样返回
    }
}
```

`SaTokenConfigure.java:19` 只做了 `StpUtil.checkLogin()`，**任何登录用户都能调用任意 `/api/**`**。该接口没有任何角色或数据范围校验。

**影响**

1. **学生可读任意点评的全部审核意见**——直接推翻 `README.md:96` 的设计承诺"学生端无审核意见"，以及 `CommentService.java:184` 注释"设计规则：审核意见永不进学生端"。
2. 学生可遍历 `id` 读取**其他班级、其他导师**的点评正文与修改前版本。
3. 答辩时若老师用 `student01` 的 token 直接请求该接口，会当场击穿整个"隐私设计"叙事——**这是本项目风险最高的单点**。

**根因**

`CommentAudit → AuditItem` 的映射写了两遍：

| 位置 | 是否裁剪 `opinion` / `beforeContent` |
| --- | --- |
| `CommentService.java:176-192`（`detail()`） | ✅ `authContext.isStudent() ? null : ...` |
| `AuditService.java:269-289`（`audits()`） | ❌ 无裁剪 |

裁剪规则只写在其中一个副本里 → 第二个副本必然漏。（对应红线 **R5**）

**修复（两步，缺一不可）**

第一步，入口加角色校验：

```java
// AuditService.java:269
public List<CommentDtos.AuditItem> audits(Long commentId) {
    requireAdmin();                     // ← 与同类其他方法保持一致
    ...
}
```

第二步，抽公共映射，消灭第二份裁剪逻辑：

```java
// 新增 common/AuditItemMapper.java
public final class AuditItemMapper {
    private AuditItemMapper() {}

    /** @param forStudent true 时裁掉内部字段 */
    public static CommentDtos.AuditItem of(CommentAudit a, boolean forStudent) {
        CommentDtos.AuditItem it = new CommentDtos.AuditItem();
        it.setId(a.getId());
        it.setResult(a.getResult());
        it.setActionType(a.getActionType());
        it.setResultLabel(CommentService.actionLabel(a.getActionType(), a.getResult()));
        it.setAuditorName(a.getAuditorName());
        it.setRound(a.getRound());
        it.setAuditAt(a.getAuditAt());
        it.setOpinion(forStudent ? null : a.getOpinion());
        it.setBeforeContent(forStudent ? null : a.getBeforeContent());
        return it;
    }
}
```

`CommentService.detail()` 与 `AuditService.audits()` 都改为调用它。

**验证（必须实测）**

```bash
# 1. 学生 token 调 history，应 403
curl -s -H "satoken: <student01-token>" http://127.0.0.1:8090/api/audit/1/history
# 期望：{"code":403,"msg":"仅教务管理员可执行审核与发布"}

# 2. 导师 token 调他人点评 history，应 403
# 3. 教务 token 调，应正常返回且含 opinion
```

**耗时**：20 分钟（含验证）

### P1-1 · 列表查询 N+1（每页约 81 次 SQL）

| 项 | 内容 |
| --- | --- |
| 位置 | `CommentService.java:352-400`（`toRow`） |

```java
// 每行都执行一次：
CommentSentiment se = sentimentMapper.selectOne(...);   // :385
CommentAudit last = auditMapper.selectOne(...);         // :392
Clazz cl = clazzMapper.selectById(s.getClazzId());      // :365  ← 未缓存
Major m = majorMapper.selectById(cl.getMajorId());      // :368  ← 未缓存
```

`pageSize=20` → `1 + 20×4 = 81` 次查询。`teacherName`（:356）与 `student`（:360）已用 Map 缓存，说明作者知道要缓存，只是漏了后两个。

**影响**：列表接口响应时间随数据量线性劣化；`AuditService.pageOf()` 也复用该方法，审核队列同样受影响。答辩演示时 56 条数据看不出问题，真实场景上千条会明显卡顿。

**修复**：按投入产出排序

| 方案 | 改动量 | 效果 |
| --- | --- | --- |
| ① 补 `clazzCache` / `majorCache` | 4 行 | 81 → 41 次 |
| ② 批量预取 sentiment / audit（`in(commentIds)` + 内存分组取最新） | ~20 行 | 41 → 5 次 |
| ③ Mapper 联表 `selectRowPage` | 新增 XML/注解 | 5 → 2 次（最优） |

**建议先做 ①②**（半小时内完成，收益最大），③ 留作优化项写入设计文档。

**验证**：开启 `log-impl` 后请求 `/api/comment/page?page=1&size=20`，数 SQL 行数 ≤ 6。

### P1-3 · 发布/撤回接口用 `Map` 收参，且会产生字符串 `"null"`

| 项 | 内容 |
| --- | --- |
| 位置 | `AuditController.java:77-89` |

```java
@PostMapping("/{id}/publish")
public R<Void> publish(@PathVariable Long id,
        @RequestBody(required = false) Map<String, Object> body) {
    String reason = body == null ? null : String.valueOf(body.getOrDefault("reason", ""));
    auditService.publish(id, reason);
}
```

两个问题：

1. **无 `@Valid`**：与同文件 `approve/return/reject`（都用 `@Valid @RequestBody CommentDtos.AuditReq`）不一致。同一控制器两套入参风格，后来者不知道跟哪个。
2. **`String.valueOf(null)` 返回字符串 `"null"`**（长度 4）。当请求体为 `{"reason": null}` 时，`getOrDefault` 返回 `null`（键存在），`String.valueOf(null)` → `"null"`。该值会进入 `checkOpinion`，报错文案是"再发布的意见至少需 5 字"，而真实原因是"没填"。

**修复**：复用 `AuditReq`（加一个 `reason` 字段），或新建 `ReasonReq { @NotBlank @Size(min=...) String reason; }`。

**验证**：`POST /api/audit/1/unpublish` body `{"reason":null}` 应返回 400 且提示"理由不能为空"，而非字数不足。

### P1-6 · `sql.init` 每次启动执行且吞掉错误

| 项 | 内容 |
| --- | --- |
| 位置 | `application.yml:22-25` |

```yaml
sql:
  init:
    mode: always              # 每次启动都跑建表脚本
    continue-on-error: true   # 出错继续，不中断启动
```

**影响**：这两项组合起来，正好**放大了你们已经踩过的坑**——`schema.sql` 缺 `action_type` / `round` 列时，建表失败被静默跳过，直到运行时抛 `Column not found`，错误现场离根因很远（当时排查花了时间）。

**修复**：
- `mode: always` → `mode: never`（生产），建表由迁移脚本负责
- `continue-on-error` → `false`（让 schema 问题在启动时就炸，而不是运行到某个接口才炸）

**验证**：故意把 `schema.sql` 改错一个列名，启动应立即失败并明确指出错误 SQL。

## 六、值得保持的 7 个实践（应写进团队规范）

这部分比问题清单更有价值——**它们证明团队有能力写出高质量代码，缺的只是把能力固化成约束**。

### ✅ 1. 统计口径唯一入口（`CommentScope.java`）

```java
/** 统计口径的**唯一入口**。... 这样"学生可见 = 纳入统计"这条业务规则
 *  只有一个实现点，想漏都漏不掉。 */
public final class CommentScope {
    private CommentScope() {}          // 工具类禁止实例化
```

**为什么好**：把"业务规则"收敛为"代码结构"，而不是靠人记住。这是本项目最值得写进论文的设计。

**推广建议**：同样的手法用到"权限范围"（`VisibleScope`）和"阈值"（`RuleConfig`）。

### ✅ 2. 状态迁移全部条件化（`AuditService` 7 个动作无一例外）

```java
.eq(Comment::getStatus, CommentStatus.PENDING)   // 条件写进 WHERE
...
if (rows == 0) throw BizException.conflict("该点评状态已变化，请刷新后重试");
```

**为什么好**：`check-then-act` 是并发双写的经典成因。这里 7 个动作（approve / return / reject / publish / unpublish / update / submit）**全部**采用条件化 UPDATE + 行数校验，一致性极高。这已经不是"碰巧写对"，而是有意识的设计。

### ✅ 3. 学生端字段在结构层裁剪（`CommentService.java:94-99`）

```java
// 学生端列表同样不携带「审核意见 / 情感标签」：
// 审核意见是教务与导师的内部沟通；情感标签的对象是导师文本，
// 展示给学生会被误读为对自己的评价。
result.getRecords().forEach(r -> {
    r.setLastOpinion(null);
    r.setLastAuditor(null);
    r.setSentimentLabel(null);
    r.setLowConfidence(false);
});
```

**为什么好**：不是"前端不显示"，而是"数据根本不下发"。注释还解释了**为什么情感标签不能给学生看**（会被误读为对自己的评价）——这是产品思维，不是编码思维。

**讽刺之处**：P0-2 的漏洞正好绕过了这道防线。**说明结构约束也需要配套的入口校验**，否则只是"主要通道安全"。

### ✅ 4. 种子数据刻意覆盖阈值两侧（`DemoDataInitializer.java:46-57`）

> *"若只有 n=3 与 n=5 两个班，实现写成 `n<4` 会同时通过（3<4 空 ✓、5<4 画 ✓），错误完全测不出来。加入 n=4 后 `n<4` 必翻红。**只测阈值两侧、不测阈值本身，任何中间错值都会全绿通过。**"*

**为什么好**：这段注释体现的是**测试设计能力**，而且是很多工作多年的工程师都不具备的。

**遗憾**：这个洞察只用在种子数据上，**没有用在自动化测试上**（见 P1-9）。把同一套思路写成 `MinSampleTest`，价值立刻翻倍。

### ✅ 5. 登录失败统一提示，防账号枚举（`AuthService.java:36-39`）

```java
// 统一提示，不区分"用户不存在"和"密码错误"，避免账号枚举
if (user == null || !passwordEncoder.matches(...)) {
    throw new BizException(401, "用户名或密码错误");
}
```

**为什么好**：短路的写法（`if (user == null) throw "用户不存在"`）更"友好"，但会泄露账号是否存在。这里选择了正确而非友好。

### ✅ 6. 全局异常统一出口 + 越权行为留痕

`GlobalExceptionHandler` 保证前端永远拿到 `{code,msg,data}`；越权尝试不只抛 403，还调用 `operLogService.record(..., false)` 记录（`CommentService.java:207,216,258`）。

**为什么好**：越权日志是安全事件的唯一线索来源。大多数学生项目只抛异常，不留痕。

---

### ✅ 7. 拒绝批量发布的设计决策（`AuditController.java:21-22`）

> *"**不提供批量发布接口**。批量更新极易写成 `WHERE id IN (...)` 的裸 SQL，绕过逐条状态校验，是状态机被破坏的主要入口。"*

**为什么好**：这是**主动放弃功能以保护不变量**的决策，并且写清了理由。答辩时这类"我为什么不做"比"我做了什么"更能体现工程判断力。
