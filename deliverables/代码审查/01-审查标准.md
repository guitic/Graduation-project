# 01 · 代码审查标准

> 本文定义"什么算问题、多严重、谁来拦"。所有条目均以本项目真实代码为依据，正例可直接作为团队范例。

---

## 一、适用范围与边界

### 1.1 什么必须走审查

| 变更类型 | 是否审查 | 说明 |
| --- | --- | --- |
| `src/main/java/**` 业务代码 | ✅ 必须 | 含 Controller / Service / Mapper |
| `src/main/resources/**` 配置、SQL、词典 | ✅ 必须 | 配置即代码，口令泄露比代码 bug 更严重 |
| `frontend/src/**` | ✅ 必须 | 含 `api/`、`views/`、`components/` |
| `pom.xml` / `package.json` | ✅ 必须 | 依赖变更 = 供应链风险 |
| `README.md` / 文档 | ⚠️ 轻审 | 只查事实错误（如端口、账号、命令） |
| 自动生成（`dist/`、`target/`、`node_modules/`） | ❌ 不审 | 应进 `.gitignore`，不入库 |
| 格式化工具的批量改动 | ❌ 不审 | 必须**独立成一个 PR**，不夹带业务改动 |

### 1.2 审查必看什么

1. **正确性**——边界条件、空值、并发、状态机是否可被绕过
2. **安全性**——鉴权、数据范围、敏感字段外泄、口令硬编码
3. **一致性**——是否复用了已有的单一入口（口径、常量、DTO 裁剪）
4. **可维护性**——后来的人能否在 5 分钟内看懂这段为什么这么写
5. **测试**——新增分支有没有对应断言

### 1.3 审查**不该**争什么

| 不该争 | 交给谁 |
| --- | --- |
| 缩进、分号、引号、换行 | Prettier / Checkstyle，**不要出现在评论里** |
| 变量叫 `data` 还是 `result` | 除非引起歧义，否则不评论 |
| "我会用另一种写法" | 除非能证明对方写法有缺陷 |
| 个人偏好的架构风格 | 项目已有约定就遵守约定；想改约定，另开 issue 讨论 |

> 一条经验：**如果评论可以写成一条 lint 规则，就不要写成人话。** 写成人话意味着这条规则会被反复提，且每次都要重新争论。

## 二、严重度分级

| 级别 | 定义 | 处置 | 典型场景 |
| --- | --- | --- | --- |
| **P0 阻断** | 安全漏洞、数据丢失/错乱、状态机可被破坏、构建失败 | **必须改，否则禁止合并**，不接受"后续修复" | 越权、明文口令、事务缺失导致双写、`WHERE` 条件写漏 |
| **P1 重要** | 正确性隐患、性能退化、规则双实现、关键路径无测试 | **必须回应**；允许"已知问题 + 建 issue + 明确排期"后合并 | N+1 查询、常量前后端双写、demo 代码进主链路 |
| **P2 建议** | 可读性、冗余、命名、小优化 | 建议采纳，作者可拒绝并说明理由 | 未 import 全限定名、DTO 复用不当 |
| **Nit 微瑕** | 纯风格 | 可不改 | 空行、注释错别字 |

### 2.1 判定口诀

- 能用一句"**攻击者/并发用户这样做会怎样**"描述出坏结果的 → **P0**
- 能用一句"**数据量涨 10 倍后这里会怎样**"描述出坏结果的 → **P1**
- 只能说"**我觉得这样更好**"的 → **P2 或 Nit**

### 2.2 一个反直觉的规则

> **P0 不允许"下次一定"。**
> 一旦允许 P0 带病合并，团队会立刻学会"P0 也可以商量"，分级体系当天失效。
> P1 允许带 issue 合并，是为了不让流程卡死；P0 不允许，是为了让流程有意义。

## 三、10 条红线（本项目定制）

红线 = 一旦触碰就是 P0，**评审者不需要解释理由，作者必须改**。

### R1 · 权限校验必须成对：入口 + 数据范围

**规则**：任何返回业务数据的接口，必须有 ① 角色校验 ② 数据范围校验。两者缺一即 P0。

- 角色校验：`requireAdmin()` / `@SaCheckRole` / `authContext.isTeacher()`
- 数据范围校验：`CommentScope.ownedByTeacher(id)` / `visibleToStudent(id)` / 显式 `teacherId.equals(c.getTeacherId())`

**为什么**：前端隐藏菜单不是鉴权。`SaTokenConfigure` 只做 `checkLogin()`，**任何登录用户都能调用任何 `/api/**`**。

**反例（真实，P0）**：
```java
// AuditController.java:91
@GetMapping("/{id}/history")
public R<List<CommentDtos.AuditItem>> history(@PathVariable Long id) {
    return R.ok(auditService.audits(id));   // ← 只校验了登录，没有角色/范围校验
}

// AuditService.java:269
public List<CommentDtos.AuditItem> audits(Long commentId) {
    // 无 requireAdmin()，且 opinion / beforeContent 原样返回
}
```
学生用自己 token 遍历 `id`，即可读到**任意点评的全部审核意见与修改前正文**——直接推翻 README 第 96 行"无审核意见"的设计承诺。

**正例（真实）**：
```java
// CommentService.java:201
private void assertCanView(Comment c) {
    if (authContext.isAdmin()) return;
    if (authContext.isTeacher()) {
        if (!authContext.currentTeacherId().equals(c.getTeacherId())) {
            operLogService.record("VIEW_COMMENT", "COMMENT", c.getId(), "越权访问他人点评", false);
            throw BizException.forbidden("无权查看该点评");
        }
        return;
    }
    Long sid = currentStudentId();
    boolean published = CommentStatus.APPROVED.equals(c.getStatus()) && c.getPublishedAt() != null;
    if (!sid.equals(c.getStudentId()) || !published) { /* 记日志 + 403 */ }
}
```

**判定方法**：对每个新增/修改的 `@GetMapping` / `@PostMapping`，问一句"**换个角色的 token 调它，会拿到不该拿的数据吗？**"

### R2 · 统计口径只能有一个入口

**规则**：所有报表、词云、下钻、导出，必须经 `CommentScope` 构造条件。禁止在业务代码里手写 `status='APPROVED' AND published_at IS NOT NULL`。

**为什么**："学生可见 = 纳入统计"是一条业务规则，两个实现点就必然有两个版本。

**正例（真实，教科书级）**：
```java
// CommentScope.java:12
public final class CommentScope {
    private CommentScope() {}                       // 工具类禁止实例化
    public static LambdaQueryWrapper<Comment> published() { ... }
    public static LambdaQueryWrapper<Comment> visibleToStudent(Long studentId) { ... }
}
```

**判定方法**：`grep -rn "getPublishedAt" src/main/java` 命中处若不在 `CommentScope` 内，逐个确认是否属于"非统计"用途（如状态机迁移，属合理例外）。

---

### R3 · 状态迁移必须条件化，禁止 check-then-act

**规则**：状态变更一律 `UPDATE ... WHERE id=? AND status=?`，并检查影响行数，0 行返 409。**禁止**先 `selectById` 判断再无条件 `updateById`。

**为什么**：两个教务同时点"通过"，check-then-act 会各写一条审核记录，时间线出现两次"通过"。

**正例（真实，全部 7 个动作都遵守了）**：
```java
// AuditService.java:139
int rows = commentMapper.update(null, new LambdaUpdateWrapper<Comment>()
        .eq(Comment::getId, id)
        .eq(Comment::getStatus, CommentStatus.PENDING)     // ← 条件写在 WHERE 里
        .set(Comment::getStatus, CommentStatus.APPROVED)
        .set(Comment::getUpdatedAt, now));
if (rows == 0) {
    throw BizException.conflict("该点评状态已变化（可能已被其他教务处理），请刷新后重试");
}
```

**判定方法**：搜 `updateById(`。命中处若改的是 `status` / `publishedAt` / `withdrawnAt`，即违规。

### R4 · 阈值与常量必须有单一来源

**规则**：同一业务阈值只能有**一个权威定义**。前端不得写字面量；如需展示，由后端接口下发。

**为什么**：门槛是答辩演示的核心（"改成 6 四张图必须同时变"），双写意味着演示当天可能不一致。

**反例（真实，P1）**：同一个"审核意见最少字数"有 3 份定义

| 位置 | 值 |
| --- | --- |
| `AuditService.java:52-58` | 5 / 10 / 10 / 20 / 10 / 5 |
| `AuditQueue.vue:197,205,213,221` | `minLen: 5 / 10 / 10 / 20` |
| `Unpublished.vue:165` | `minLen: rePublish ? 5 : 0` |

**修复方向**：`/api/auth/me` 或独立的 `/api/config/rules` 下发 `{approvePublish:5, approveOnly:10, return:10, reject:20, unpublish:10, republish:5}`，前端 `ACTIONS` 从响应填充；后端保留常量作为唯一权威。

**判定方法**：在 diff 里看到 `5`、`10`、`20`、`3`、`0.7` 这类裸数字且带业务含义 → 追问"这个数字的权威定义在哪"。

---

### R5 · DTO 字段裁剪只能有一处实现

**规则**：同一实体的出参映射必须收敛到一个方法。**裁剪规则写在映射里，不写在调用方**。

**为什么**：两处映射 = 两套裁剪策略 = 必有一处漏。

**反例（真实，P1，且是 P0 漏洞的根因）**：

| 方法 | 是否裁剪 `opinion` / `beforeContent` |
| --- | --- |
| `CommentService.detail()` :185,189 | ✅ `authContext.isStudent() ? null : ...` |
| `AuditService.audits()` :281,285 | ❌ 原样返回 |

两个方法都在做 `CommentAudit → AuditItem` 的映射。第二个忘了裁，就有了 P0。

**修复方向**：抽 `AuditItemMapper.of(CommentAudit a, boolean forStudent)`，两处都调它；`forStudent` 由 `authContext` 在边界处求值一次。

**判定方法**：同一个 DTO 的 `setXxx` 在 ≥2 个方法里出现 → 要求合并。

---

### R6 · 分页查询禁止 N+1

**规则**：列表接口的 SQL 次数必须是常数级（≤ 6），不随 `pageSize` 增长。

**反例（真实，P1）**：`CommentService.toRow()` 每行触发 4 次查询
```java
// CommentService.java:352-400
CommentSentiment se = sentimentMapper.selectOne(...);   // 每行 1 次
CommentAudit last = auditMapper.selectOne(...);         // 每行 1 次
Clazz cl = clazzMapper.selectById(s.getClazzId());      // 每行 1 次（未缓存）
Major m = majorMapper.selectById(cl.getMajorId());      // 每行 1 次（未缓存）
```
`pageSize=20` → 1 + 20×4 ≈ **81 次 SQL**。`teacherName` 和 `student` 已用 Map 缓存，说明作者知道要缓存，只是漏了后两个。

**修复方向**：三选一
1. 缓存：`clazzCache` / `majorCache` / 批量预取 `sentimentMapper.selectList(in commentIds)` 和 `auditMapper` 按 `commentId` 分组取最新一条
2. 联表：Mapper 里写一个 `selectRowPage`，一次 JOIN 出全部展示字段
3. 反范式：`comment` 表冗余 `clazz_name` / `major_name`（写入时同步，读多写少场景最优）

**判定方法**：看 `for` / `forEach` 循环体里有没有 `Mapper` 调用。有 → P1。

### R7 · 配置零明文密钥，演示能力必须 profile 隔离

**规则**：① 口令、密钥、token 不得出现在入库文件里；② 只服务于演示的代码（种子数据、账号列表、SQL 全量打印）不得进入生产 profile。

**反例（真实，P1，3 处）**：
```yaml
# application.yml:20
password: 123456                          # ← 明文入库
```
```java
// AuthService.java:123
return Map.of("password", "123456", ...);  // ← 硬编码口令，且 /api/demo/** 免鉴权
```
```java
// DemoDataInitializer.java:27
@Component                                 // ← 无 @Profile，生产也注入 17 个账号
```
```yaml
# application.yml:30
log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   # ← 生产打印全量 SQL（含点评正文）
```

**修复方向**：
```yaml
password: ${DB_PASSWORD:}                 # 环境变量注入，本地用 .env（已 gitignore）
```
```java
@Profile({"demo", "dev"})                 # 种子数据与账号列表仅演示/开发
@Component
public class DemoDataInitializer { ... }
```
SQL 日志移到 `application-dev.yml`。

**判定方法**：diff 里出现 `password:`、`secret`、`token`、`@Component` 且类名含 Demo/Init/Mock → 追问"生产环境跑不跑"。

### R8 · 脚本与配置必须单一事实来源

**规则**：同一份 schema / 词典 / 常量表，仓库里只能有一份。需要多处时用构建期复制，不靠人工同步。

**为什么**：这条是你们**已经踩过的坑**——`resources/db/schema.sql` 与 `sql/schema.sql` 不同步，导致启动报 `Column "action_type" not found`，当时是靠人工 `cp` 修好的。

**修复方向**：`pom.xml` 加 `maven-resources-plugin`，构建时从 `sql/schema.sql` 复制到 `target/classes/db/`，删除 `resources/db/schema.sql`。或反向：只保留 `resources/db/`，`sql/` 下放一个 README 指向它。

**判定方法**：`find . -name "*.sql"` 出现同名文件 → P1。

---

### R9 · 免鉴权接口必须集中声明且可枚举

**规则**：`excludePathPatterns` 只能出现在 `SaTokenConfigure` 一处；新增白名单必须在 PR 描述里单独说明理由。

**正例（真实）**：`SaTokenConfigure.java:21-25` 集中声明了 3 条白名单，做得对。

**需要盯的是**：白名单里 `/api/demo/**` 覆盖了 `demoAccounts()`——该接口返回明文口令。**白名单本身没错，错在它返回的东西**（见 R7）。

**判定方法**：diff 里出现 `excludePathPatterns` 或 `permitAll` → 追问"这个接口匿名可访问时，会泄露什么"。

---

### R10 · 新增业务分支必须有对应断言

**规则**：新增 `if` / `switch` 分支、新增状态迁移、新增门槛判定，必须在 `src/test` 里有对应用例。**状态机类改动，测试是合并的前提**。

**现状（P1）**：后端仅 1 个测试类 `SentimentEvalTest`（评估脚本性质）。27 项端到端验收写在 `%TEMP%/mc_test.py`——**在临时目录，未入库，重启即失**。

**最小可用要求**（不追求覆盖率数字）：
- 状态机：每个迁移的"合法路径"+"非法路径"各 1 条
- 门槛：阈值两侧各 1 条（n=4 空、n=5 放行）
- 越权：每个角色 × 每个敏感接口 1 条 403 断言

> 你们在种子数据设计上已经悟到了这个道理（`DemoDataInitializer` 注释：*"只测阈值两侧、不测阈值本身，任何中间错值都会全绿通过"*）——**把这个洞察用到测试上**。

## 四、分层检查清单

> 用法：提 PR 前作者自检；评审时按清单扫，**不逐字读代码**。

### 4.1 后端 Java（Spring Boot + MyBatis-Plus）

- [ ] Controller 只做参数绑定与转发，业务判断在 Service
- [ ] 入参用 `@Valid` + 具体 DTO，**不用 `Map<String, Object>`**
- [ ] 写操作有 `@Transactional`；只读查询加 `readOnly = true`
- [ ] 事务内不做 CPU 密集/远程调用（如 HanLP 分词应移出事务）
- [ ] 状态变更走条件化 UPDATE（R3）
- [ ] 列表查询无循环内 Mapper 调用（R6）
- [ ] 出参不直接返回 Entity，必须转 DTO
- [ ] 异常抛 `BizException`，不 `e.printStackTrace()`
- [ ] 新增 Mapper 方法有对应索引支撑（`EXPLAIN` 无 `ALL` 全表扫）

### 4.2 前端 Vue 3

- [ ] 单文件 ≤ 400 行；超出则拆子组件或抽 composable
- [ ] 图表 / 请求逻辑抽到 `composables/`，`.vue` 只留模板与状态
- [ ] 接口调用只走 `src/api/*`，不在组件里直接 `axios`
- [ ] 后端返回的 `code !== 0` 由 `request.js` 统一处理，组件不重复判断
- [ ] 业务阈值不写字面量（R4），从接口或常量模块取
- [ ] `v-for` 有稳定 `:key`，不用 index
- [ ] 异步请求有 loading 态与失败兜底
- [ ] 空态有专门组件（已有 `GateEmpty.vue`，复用而非新写）
- [ ] 敏感信息（口令、内部字段）不出现在模板里

### 4.3 SQL / 数据

- [ ] 建表语句幂等（`IF NOT EXISTS`）
- [ ] 新增查询字段有索引；`LIKE '%x%'` 明确接受全表扫
- [ ] `IN (...)` 列表有上限（防超长 SQL）
- [ ] schema 只有一份来源（R8）
- [ ] 迁移脚本可重复执行

### 4.4 安全专项

- [ ] 每个接口：谁可以调、能拿到什么范围的数据（R1）
- [ ] 敏感字段（审核意见、情感标签、内部备注）在**出参层**被裁掉，不靠前端隐藏
- [ ] 无明文口令/密钥入库（R7）
- [ ] 登录失败提示统一，不泄露"用户是否存在"（已有，保持）
- [ ] 越权尝试有审计日志（已有 `operLogService.record(..., false)`，保持）
- [ ] Token 存储方式的风险已登记（localStorage 可被 XSS 读取）

### 4.5 测试

- [ ] 新增分支有断言（R10）
- [ ] 测试不依赖执行顺序、不依赖真实时间（用 `YearMonth.now()` 相对时间，已有范例）
- [ ] 验收脚本已入库，能一条命令跑
- [ ] 修 bug 的 PR 附带能复现该 bug 的用例

### 4.6 文档与提交

- [ ] Commit message 说清"为什么"，不只说"改了什么"
- [ ] 改了口径/阈值/状态机 → 同步 `README.md` 与 `设计文档.md`
- [ ] 新增配置项 → 同步 `application.yml` 注释与 README 的"常见问题"
- [ ] 不提交 `dist/`、`target/`、`.env`、IDE 配置

## 六、规模与复杂度阈值

超过阈值不一定是错，但**必须在 PR 描述里说明理由**，否则视为 P2。

| 指标 | 阈值 | 现状 |
| --- | --- | --- |
| 单文件行数 | ≤ 400 | `Dashboard.vue` 957 ❌ |
| 单方法行数 | ≤ 50 | `CommentService.applyFilters` 50 ⚠️ 临界 |
| 方法参数个数 | ≤ 4 | `toRow(c, tNameCache, sCache)` 3 ✅ |
| 单 PR 有效变更行数 | ≤ 400 | — |
| 单 PR 涉及主题数 | 1 | — |
