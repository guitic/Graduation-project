# 代码审查机制 · 总览

> 面向 `mentor-comment-system`（Spring Boot 3.2.5 + Vue 3）的代码审查标准与流程。
> 制定依据：对现有 5,439 行核心代码的**实测基线审查**（见 `04-基线审查报告.md`），不是通用模板。
>
> **落地状态（2026-10-26）**：P0 全部完成、工具链与 CI 已接入、10 条权限断言已入库。
> 改动明细与运行时验证证据见 **`05-修复记录.md`**。


---

## 一、先说结论

你们的代码质量**不是"参差不齐"，而是"高水平设计 + 零工程约束"**。

基线审查发现：`CommentScope` 单一统计口径、状态迁移条件化 UPDATE、学生端 DTO 结构裁剪——这几处是教科书级做法，比很多商业项目做得好。但同时存在：

| 体检项 | 实测值 | 应有值 |
| --- | --- | --- |
| 版本控制 | **无 `.git`** | 必须有 |
| Lint / 格式化配置 | **0 个** | 前后端各 1 套 |
| CI 流水线 | **0 条** | ≥ 1 条 |
| 后端测试类 | **1 个**（评估脚本性质） | Service 层全覆盖 |
| 单文件最大行数 | **957 行**（`Dashboard.vue`） | ≤ 400 行 |
| 越权漏洞 | **1 处（P0）** | 0 |

**根因判断**：好的部分来自设计者的自觉，坏的部分来自**没有任何机制阻止坏代码合入**。靠自觉的质量无法在多人协作下复现，也无法在时间压力下守住。

所以这份文档的重心不是"教怎么写好代码"，而是**把已经证明有效的做法固化成规则，把已经出现的坑固化成闸门**。

## 二、三层机制（缺一层就会失效）

```
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层  流程      PR 模板 · 双人规则 · 门禁 · SLA           │  ← 保证"每次改动都被看过"
├─────────────────────────────────────────────────────────────┤
│ 第 2 层  清单      10 条红线 · 分层检查表 · 严重度分级        │  ← 保证"看的时候不漏关键项"
├─────────────────────────────────────────────────────────────┤
│ 第 1 层  工具      ESLint · Prettier · Checkstyle · CI       │  ← 保证"机器能判的不占用人的注意力"
└─────────────────────────────────────────────────────────────┘
```

**顺序不能颠倒**。先上第 2、3 层而不上第 1 层，评审者会把精力耗在缩进和分号上，真正的越权漏洞反而被淹没——这正是当前代码里 P0 漏洞能存活的原因之一。

| 周 | 目标 | 关键动作 | 进度 |

| 第 1 周 | **止血** | P0 全部完成。重点是把越权漏洞补掉、把代码纳入版本控制 | ✅ 已完成 |
| 第 2 周 | **上闸门** | CI 跑起来，PR 模板生效。此时开始"所有改动必须过 PR" | ✅ 配置就绪，待托管仓库 |

**下一步建议按这个顺序**（每项单独一个 PR）：

1. **P1-4 门槛常量单一来源** —— 答辩演示直接相关，改动小、收益立即可见
2. **P1-1 N+1（先只补两个 cache，4 行）** —— 81 次 SQL 降到 41 次，风险最低的第一步
3. **P1-5 / P1-6 / P1-7 配置分层** —— 三项属同一主题，应一次性改完并更新 README
4. **P1-8 拆 `Dashboard.vue`** —— 结构性重构，放最后，需逐图对比验证

## 六、一句话原则

> **机器能判的交给工具，重复出现的交给红线，一次性的交给人的判断力。**
> 评审者只在"机器判不了、也没形成规则"的地方花时间——这才是审查的价值所在。
