# 02 · 代码审查流程

> 流程的目标不是"多一道关卡"，而是**让每次改动都有一个明确的、可预期的、有期限的判定**。
> 无期限的审查 = 阻塞；无标准的审查 = 吵架；无门禁的审查 = 建议。

---

## 一、角色与职责

| 角色 | 谁担任 | 职责 | 不做 |
| --- | --- | --- | --- |
| **作者** | 提交 PR 的人 | 自检清单 → 写清 PR 描述 → 响应评论 → 合并 | 不自审自批（单人模式见 §8） |
| **评审者** | 任一非作者成员 | 按 `01-审查标准.md` 分级 → 24h 内给首轮结论 | 不替作者改代码；不纠结风格 |
| **裁决者** | 项目负责人 | 打破"这算不算 P0"的僵局；批准例外 | 不参与日常评审 |

**规模约定**：3 人及以下不设专职评审者，**交叉评审**即可（A 写 B 审，B 写 A 审）。1 人开发走 §8 降级方案。

---

## 二、分支模型（够用即可，不引入 GitFlow）

```
main ───●──────────●──────────●──────────●───→  受保护，只接受 PR 合并
         \        / \        / \        /
          ●──●──●    ●──●──●    ●──●──●
         feat/xxx   fix/xxx    chore/xxx        短生命周期，≤ 3 天
```

| 分支 | 命名 | 生命周期 | 合入方式 |
| --- | --- | --- | --- |
| `main` | — | 永久 | 受保护，禁直推 |
| 功能 | `feat/comment-withdraw` | ≤ 3 天 | Squash merge |
| 修复 | `fix/audit-history-403` | ≤ 1 天 | Squash merge |
| 重构/格式 | `chore/eslint-setup` | ≤ 1 天 | Squash merge |
| 紧急 | `hotfix/xxx` | ≤ 2 小时 | 允许直推 main，**24h 内补 PR 追审** |

**为什么 ≤ 3 天**：分支活过 3 天，冲突概率指数上升，评审者面对 800 行 diff 会直接 LGTM——这是橡皮章评审的头号成因。

## 三、PR 规范

### 3.1 硬性要求

| 项 | 要求 | 不满足的后果 |
| --- | --- | --- |
| 标题 | `<type>(<scope>): <做了什么>`，如 `fix(audit): history 接口补角色校验` | 打回 |
| 描述 | 必须填模板中的「为什么」「怎么验证」 | 打回 |
| 变更行数 | 有效变更 ≤ 400 行（不含 lock 文件、格式化） | 要求拆分 |
| 主题数 | 1 个 | 要求拆分 |
| 自检清单 | 10 条逐条勾选 | 打回 |
| CI | 全绿 | 禁合并 |
| 关联 issue | 修 bug 必须关联 | 打回 |

### 3.2 拆分原则

一个 PR 只回答一个问题。以下情况**必须拆**：

- 同时改了后端和前端 → 拆成"后端接口"+"前端对接"（后端先合，前端再合）
- 同时做了重构和加功能 → 拆成"重构（行为不变）"+"加功能"
- 同时做了格式化和业务改动 → 格式单独一个 PR

> 拆分不是形式主义。**行为不变的重构**才能被安全地快速评审；混在一起，评审者无法判断某行改动是"搬家"还是"改逻辑"。

## 四、审查流程（标准路径）

```
作者                                    评审者                        系统
 │
 ├─ 1. 本地自检（速查卡 10 条）
 ├─ 2. 推分支，开 PR（填模板）
 ├─ 3. 等 CI ────────────────────────────────────────────────→ 门禁①：构建+lint+测试
 │                                                    ✗ 红 → 作者修，评审者不看
 │                                                    ✓ 绿 ↓
 ├─ 4. 请求评审 ──────────────────────→ 5. 24h 内首轮
 │                                       ├─ 逐条按 P0/P1/P2 标注
 │                                       ├─ 给结论：Request changes / Approve
 │                                       └─ P0 必须写"怎么改"
 │
 ├─ 6. 响应评论
 │     ├─ 接受 → 改代码 → 回复"已改，见 <commit>"
 │     ├─ 不接受 → 说明理由 → 评审者撤回或升级裁决者
 │     └─ P1 延后 → 建 issue + 在 PR 里贴链接
 │
 ├─ 7. 重新请求评审（仅当有 P0 改动时）
 │
 └─ 8. Squash merge ─────────────────────────────────────────→ 门禁②：1 个 Approve
                                                              门禁③：无未解决 P0
```

### 4.1 三道门禁

| 门禁 | 判定 | 谁来保证 | 绕过方式 |
| --- | --- | --- | --- |
| ① CI 绿 | 构建 + lint + 测试全过 | 系统自动 | 无（不允许 `--no-verify`） |
| ② 至少 1 个 Approve | 非作者的成员批准 | 平台分支保护 | 无 |
| ③ 无未解决 P0 | 所有 P0 评论已 resolve | 评审者 + 作者 | 裁决者书面批准（记录在 PR） |

### 4.2 什么情况下可以只做"轻审"

| 场景 | 轻审标准 |
| --- | --- |
| 只改文档 / 注释 | 查事实正确性即可，不必跑全流程 |
| 只改 `README` 里的命令 | 复制粘贴实测一遍 |
| 依赖小版本升级（patch） | CI 绿即可，看一眼 changelog 有无 breaking |
| 纯格式化 PR | 确认 diff 只有空白变化（`git diff -w` 为空） |

## 五、时效约定（SLA）

| 环节 | 时限 | 超时处理 |
| --- | --- | --- |
| 评审者首轮响应 | **24 小时**（工作日） | 作者可 @ 裁决者，或换人评审 |
| 作者响应评论 | **48 小时** | PR 标记 `stale`，一周未动则关闭 |
| 紧急修复追审 | **24 小时**内补 PR | 逾期在周会通报 |
| 单轮评审往返次数 | ≤ 3 轮 | 第 4 轮说明 PR 太大或标准不清，升级裁决者 |

> **24 小时不是形式**。审查的最大成本不是评审者花的时间，而是作者**等待时的上下文丢失**——等三天后回来改，等于重新理解一遍自己的代码。

## 六、评论分级与话术

### 6.1 五级标签（每条评论必须带前缀）

| 前缀 | 含义 | 作者必须 |
| --- | --- | --- |
| `[P0]` | 阻断，必须改 | 改，或升级裁决 |
| `[P1]` | 重要，需回应 | 改，或建 issue 并贴链接 |
| `[P2]` | 建议 | 可拒绝，说明理由即可 |
| `[Nit]` | 微瑕，可不改 | 随意 |
| `[Q]` | 提问，不是判定 | 回答即可 |
| `[赞]` | 值得保持的做法 | — |

**没有前缀的评论 = 没有结论**，作者有权不处理。

### 6.2 话术模板

**P0（说清后果 + 给方向）**
```
[P0] 这里缺数据范围校验。

现象：任意登录用户可用自己 token 遍历 id 调用 /api/audit/{id}/history，
      拿到全部 opinion 与 beforeContent，与「审核意见永不进学生端」的
      设计承诺冲突。

建议：在 audits() 入口加 requireAdmin()；若确需给学生看时间线，
      走 CommentService.detail() 的裁剪分支，不要开第二条映射路径。

验证：student01 token 调 GET /api/audit/1/history 应返回 403。
```

**P1（给量化的坏结果）**
```
[P1] toRow() 里每行 4 次查询，pageSize=20 时约 81 次 SQL。

clazz / major 已经有 sCache 的模式，补两个 cache 即可降到 5 次左右。
如果这次来不及，建议建 issue 并标注「数据量上千后列表会明显变慢」。
```

**P2（给出理由，允许拒绝）**
```
[P2] logout 里用了全限定名 cn.dev33.satoken.stp.StpUtil.logout()，
同文件其他地方都是 import 后直接用。建议统一。
不影响功能，你决定。
```

**质疑设计（用提问，不用断言）**
```
[Q] 这里为什么把 HanLP 分词放在 @Transactional 里面？
    分词是纯 CPU 计算，会让事务持有时间从毫秒级拉到几十毫秒。
    是有意为之（保证分析结果与发布同生共死），还是可以移到事务外？
```
> 提问式的好处：如果对方有理由，你学到了；如果没有，对方自己就改了。

**表扬要具体**
```
[赞] CommentScope 把「已发布」口径收敛成唯一入口，注释还写明了
     「想漏都漏不掉」。这个做法建议推广到阈值常量（见 R4）。
```

### 6.3 禁止的话术

| ❌ 不要说 | ✅ 改成 |
| --- | --- |
| "这里写得不好" | "这里在 X 场景下会 Y，建议 Z" |
| "为什么不用 XXX？" | "用 XXX 的话能解决 Y，有考虑过吗？" |
| "重写吧" | "P0 有 3 处，建议先修 A/B/C；D/E 可以后续" |
| "LGTM"（无任何评论） | 至少说明"看了哪些文件、哪部分没细看" |
| "按我说的改" | 给出理由；理由不成立时作者有权拒绝 |

## 七、例外与升级

| 场景 | 处理 |
| --- | --- |
| 答辩前 24h 内的紧急修复 | 允许直推，**必须**在 24h 内补 PR 追审；PR 描述注明 `hotfix` |
| 评审者与作者对严重度有分歧 | 裁决者判定，**一次定论**，不反复拉扯 |
| 确实需要违反某条红线（如临时保留明文口令做演示） | 裁决者书面批准 + PR 内 `// TODO(security): 答辩后移除` + 建 issue，**不允许无记录例外** |
| 评审者 24h 无响应 | 换人；连续 2 次超时，在周会调整分工 |

> 例外的关键是**留痕**。允许例外但要求记录，团队会自然减少例外；允许例外且不留痕，红线三个月内必然失效。

## 八、单人开发降级方案（毕业设计常见）

一个人开发时，"交叉评审"不成立，但**审查的动作不能省**——否则等于没有机制。用以下替代：

### 8.1 延迟自审（最有效）

1. 写完 → **不立刻提交**，去做别的事或睡一觉
2. ≥ 12 小时后回来，**以评审者视角读自己的 diff**（只看 diff，不看上下文）
3. 按速查卡 10 条逐条过，把发现写成 PR 评论（自己给自己留评论）

> 为什么有效：刚写完时代码在脑子里，看不出歧义；隔 12 小时，你和"未来的维护者"视角接近了。

### 8.2 工具替代人

| 人本该做的 | 单人模式下由谁做 |
| --- | --- |
| 发现格式问题 | Prettier / Checkstyle |
| 发现空指针、未使用变量 | IDE 检查 + ESLint |
| 发现 SQL 慢查询 | `EXPLAIN` + MyBatis 日志数 SQL 条数 |
| 发现越权 | **自己写 403 断言测试**（这是唯一无法自动化的，必须靠用例） |
| 发现重复逻辑 | `grep` 同名 DTO 的 `setXxx` 出现次数 |

### 8.3 强制自问三句（写在 PR 描述里）

1. 这个改动**最可能怎么坏**？（写出具体场景，不是"可能会出错"）
2. 我怎么**验证它没坏**？（命令 / 测试 / 截图）
3. 半年后的人看这段，**需要哪条注释**才能看懂"为什么"？

### 8.4 用 AI 做第一轮

单人项目可以把自己的 diff 交给 AI 做首轮扫描，重点问：
- "这段代码有没有权限绕过？"
- "这个循环里有没有重复查询？"
- "同一个常量在项目里出现了几次？"

> 但 AI 的结论必须自己复核。AI 擅长发现"模式不匹配"，不擅长判断"这个业务场景是否真的会发生"。

## 九、度量（只记 4 个数，不搞仪表盘）

| 指标 | 定义 | 健康值 | 说明 |
| --- | --- | --- | --- |
| **首轮通过率** | 首次评审即 Approve 的 PR 占比 | 30%~60% | >80% 说明评审在走过场；<20% 说明标准没对齐 |
| **PR 中位行数** | 有效变更行数中位数 | ≤ 200 | 持续 >400 说明拆分纪律失效 |
| **逃逸缺陷数** | 合并后才发现的问题数 | 趋近 0 | 每发现 1 个，回溯"哪条红线本该拦住"并补规则 |
| **评审耗时中位数** | 开 PR → 首个 Approve | ≤ 24h | 超时是流程失效的第一信号 |

**每月看一次**，重点不是数字好看，而是**逃逸缺陷的回溯**：

```
逃逸缺陷 → 问三个问题
  ① 这是哪类问题？（权限 / 并发 / 性能 / 边界）
  ② 现有红线能拦住吗？
     ├─ 能，但没人执行 → 问题在流程执行，不在标准
     └─ 不能 → 补一条红线（这才是标准迭代的唯一正确来源）
  ③ 有测试能复现吗？没有就补上。
```

## 十、五种反模式（出现即流程失效）

| 反模式 | 表现 | 后果 | 对策 |
| --- | --- | --- | --- |
| **橡皮章** | 30 秒 Approve，无任何评论 | 审查归零，但团队以为有保障 | 强制"至少指出 1 处可改进或明确说'本 PR 无 P0/P1'" |
| **风格之争** | 评论里争论命名、缩进 | 消耗信任，真问题被淹没 | 能写成 lint 规则的，一律进工具 |
| **改需求式评审** | "顺便把这块也重构了吧" | PR 无限膨胀，永远合不进去 | 新想法 → 新 issue，不在本 PR 做 |
| **作者防御** | 每条评论都辩解 | 评审者不再提意见 | 分歧升级裁决者，一次定论 |
| **大 PR 惯性** | "这次改动太多，拆不动了" | 评审质量断崖下降 | 硬性 400 行上限；拆不动说明设计有问题 |

## 十一、流程速记

```
自检 10 条 → 开 PR（填模板）→ CI 绿 → 24h 内评审
   → P0 必修 / P1 可延 / P2 可拒 → 1 个 Approve → Squash merge
```

**记住三件事**：
1. 评论必须带 `[P0]/[P1]/[P2]` 前缀，否则没有结论
2. P0 不允许"下次一定"
3. 例外必须留痕，否则红线三个月内失效
